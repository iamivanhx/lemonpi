## Summary

Pi's global package declarations live in `<agent-dir>/settings.json`; `--local` changes project `.pi/settings.json` and needs project trust. `update --extensions` considers **both** scopes; targeted update matches identity, not exact source spelling, and also considers both scopes. Exact npm version pins are skipped during update; git refs are fetched/reconciled to the configured ref, not rewritten. Source identity normalizes git transport, `.git`, and ref to host/path. `pi list` is human-formatted, scope-labelled and has **no `--json`**; inspect settings for structured declarations instead (but do not infer effective project loading without trust). Package object filters survive install/source replacement and only narrow resources. Pi documents a settings JSON schema, not a Pi-specific package version-compatibility constraint. `agents/*.md` and `subagents.json` are **tintinweb extension**, not Pi-core, conventions. ## Install, remove, update and list scope/output

- Plain `pi install <source>` persists a source in user `<agent-dir>/settings.json` after installing; `pi install --local <source>` uses `.pi/settings.json` and project package storage. Plain `remove` removes from user storage/settings; `remove --local` uses project storage/settings. `uninstall` aliases `remove`; `config` accepts `--local`. Local-path install checks existence but does not copy it; remove doesn't delete the local source. [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#install-and-manage-packages), [cli.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#package-commands), [package-manager.js `installAndPersist`/`removeAndPersist`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L783-L832).
- Bare `pi update` updates Pi **itself**, not extensions. `pi update --extensions` considers configured user **and trusted project** packages; `pi update --extension <source>` aliases `pi update <source>` and matches same package identity in *both* scopes, not just one scope. `--all` includes Pi; `update` has no `--local` option. Untrusted project entries aren't loaded into the settings manager. [cli.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#update-pi-or-packages), [package-manager.js `update`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L833-L910), [settings-manager.js `loadFromStorage`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/settings-manager.js).
- `pi list` prints separate `User packages:` / `Project packages:` sections, configured source strings, `(filtered)` for object entries, and an indented installed path **if one exists**. An empty list says `No packages installed.` This is human-oriented text, not a documented stable machine protocol; `pi list --json` fails `Unknown option --json for "list"` (observed exit 1). `pi list --help` lists only trust switches, not JSON. `--no-approve` omits trust-gated project packages; `--approve` includes them. A declaration appearing in `list` does not guarantee it is installed or effectively loaded. [package-manager.js `listConfiguredPackages`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L759-L781), [CLI implementation (bundled) `case "list"`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/bundle/chunks/chunk-MM3LKT73.js), [CLI help](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#package-commands). **Observation**: in fresh temporary agent/cwd, `pi list --no-approve` printed only user entries, `pi list --approve` printed both; see experiment below.

## Pins and update behavior

- Sources include `npm:@scope/pkg@1.2.3` and `git:github.com/org/repo@v1` (also git commit SHA). In source, npm `pinned` means a *valid exact semver* (`semver.valid`); npm ranges/tags are not exact pins. `updateConfiguredSources()` **skips exact-version npm entries entirely**, even if the installation is missing; other npm versions are checked/installed as needed. Git entries **including refs** are processed, fetching/checking out `source.ref` while leaving the configured source string unchanged. An unref'd git checkout updates its selected upstream. The docs call git tags and commits pinned; a ref naming a movable branch/tag can resolve to different content if the remote ref moves (inference from fetch-by-ref, not an immutability guarantee). [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#choose-a-source), [package-manager.js `isExactNpmVersion`, `updateConfiguredSources`, `updateGit`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L44-L50).
- `pi update --extension <source>` and `pi update --extensions` share this pin handling (the former passes the selected identity, the latter passes all sources to the same updater). `PI_OFFLINE` short-circuits package update; avoid applying this observation to a non-offline install without considering network/package-manager failures. [package-manager.js `update` and `updateConfiguredSources`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L833-L911), [environment-variables.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/environment-variables.md#pi-process-configuration).

## Object-form package entries and filters

- `packages` accepts strings or objects of shape `{ "source": "npm:@example/pi-tools", "autoload": true, "extensions": ["extensions/*.ts", "!extensions/legacy.ts"], "skills": [], "prompts": ["prompts/review.md"], "themes": [] }`; all resource arrays and `autoload` are optional. Omitted array allows all resources permitted by package manifest; `[]` allows none; `!pattern` glob exclude, `+path` exact include, `-path` exact exclude. Filters **cannot** expose resources the package manifest did not allow. `autoload:false` changes default to empty/explicit filtering; specifically a same-identity project entry with `autoload:false` acts as a delta on the user package rather than replacing it. [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#select-package-resources), [settings-schema.js `PackageSourceSchema`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/settings-schema.js#L119-L130), [package-manager.js `dedupePackages`/`findAutoloadDeltaBase`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L1392-L1433).
- `install/remove/update` take a **source string**, not an object. `install` looks for a same-identity entry in its selected scope and, if present, replaces only its `source` (preserving object filters and `autoload`); if source already matches, it leaves the entry as-is. `remove` matches and deletes matching object entries in the selected scope; `update` reads the embedded source and does not rewrite its filters. Pi does **not** use `install` to set resource filters; edit settings or `pi config`. [package-manager.js `addSourceToSettings`/`removeSourceFromSettings`/`update`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L625-L675), [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#select-package-resources).

## Source forms and identity

- Accepted git forms include `git:github.com/x/y`, `https://github.com/x/y`, `.git` suffix, `git:git@github.com:x/y`, `ssh://git@github.com/x/y`, and optional `@ref`. The `git:` prefix allows shorthand; without it a protocol URL is required (`git@host:...` alone is not parsed as git by `parseGitUrl`). Source parser removes terminal `.git` for its normalized path, ignores ref/transport for identity and uses `git:${host}/${path}`. In a read-only test of **installed Pi 1.4.0** `parseGitUrl`, all five forms above returned identity `git:github.com/x/y` (see experiment). [cli `install --help` examples](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#package-commands), [utils/git.js](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/utils/git.js#L75-L194), [package-manager.js `getSourceMatchKeyForInput`/`getPackageIdentity`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L1100-L1140).
- Thus **within one scope** installing `git:github.com/x/y` with declared `https://github.com/x/y[.git]` replaces the matching declaration (with its spelling) rather than appending a second one **if install succeeds**; removing by any equivalent spelling removes matching declaration. User/project may *each* contain an entry: project wins loading by identity except `autoload:false` delta; `list` still lists both declarations. `update <source>` matches both scopes by identity. Npm matches package name regardless of version; local paths match absolute path resolved relative to their *settings file* for stored entries vs cwd for CLI input. [package-manager.js matching/add/dedupe/update](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L625-L675), [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#understand-scope-and-identity). **Caution observed in temp test:** project `.pi/settings.json` entry `"./pkg"` denotes `.pi/pkg`, so `pi install ./pkg --local` (cwd `pkg`) added `"../pkg"` rather than treating `"./pkg"` as the same path. [packages.md local path rule](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#choose-a-source).

## Project-local trust and management isolation

- Project `.pi/settings.json` and project extensions/skills/prompts/themes/MCP/system prompts require trust; exception: `sessionDir` is read from project settings before trust, and AGENTS.md/CLAUDE.md context files are not trust gated. Precedence: CLI `--approve`/`--no-approve`, user/CLI `project_trust` extension event, closest saved decision from `<agent-dir>/trust.json`, then **global-only** `defaultProjectTrust: "ask"|"always"|"never"` (default ask). Noninteractive without another decision: ask and never skip project-protected resources; always loads them. CLI overrides last one process only. [security.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/security.md#understand-project-trust), [configuration.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md).
- **Supported management-command isolation:** invoke e.g. `pi list --no-approve`, `pi update --extension npm:name --no-approve`, `pi install npm:name --no-approve`, `pi remove npm:name --no-approve` to ignore trust-gated project config even if project would normally be trusted. `--local --no-approve` is refused (`Project is not trusted. Use --approve to modify local package config.` observed in temp test). For strongest isolation from project-context files (not gated) and cwd-sensitive configuration, also run from an unrelated temp cwd, with `PI_CODING_AGENT_DIR` directed to a throwaway dir when experimenting. **Do not mistake `--no-approve` for a sandbox:** global extensions can affect trust decisions, context files may still load, and Pi commands/extensions run with user's OS permissions. [CLI](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/cli.md#aliases-and-command-options), [security.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/security.md#understand-project-trust), [configuration.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md).

## Settings schema and generated fields

- User config `<agent-dir>/settings.json` defaults to `~/.pi/agent/settings.json`; project settings `.pi/settings.json` override scalar/object preferences, while resource lists are combined. `PI_CODING_AGENT_DIR` overrides the agent dir. `settings.json` supports `"$schema": "https://pi.dev/schemas/settings.schema.json"` (installed schema also at `schemas/settings.schema.json`). Core keys of interest: `defaultProvider`: string; `defaultModel`: string; `defaultThinkingLevel`: `off|minimal|low|medium|high|xhigh|max` (default medium); `modelThinkingLevels`: exact `provider/modelId` keys mapped to those levels; `theme`: string (default system); `defaultProjectTrust`: `ask|always|never` (global only). For **full settings list and types** see installed [settings.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/settings.md) and [settings.schema.json](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/schemas/settings.schema.json); [configuration.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/configuration.md), [environment-variables.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/environment-variables.md#pi-process-configuration).
- The schema also includes **Pi-managed state**: `lastChangelogVersion` is set by interactive changelog display on initial/subsequent version discovery, in global settings; `trackingId` is generated when analytics is enabled; `deviceId` is generated when authentication needs a stable installation UUID (global only). Do not assume all schema keys are desired declarative settings, or overwrite unrelated existing fields. [settings-schema.js fields/descriptions](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/settings-schema.js#L139-L205), [interactive-mode.js `getChangelogForDisplay`](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/modes/interactive/interactive-mode.js#L990-L1010), [settings-manager.js setters](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/settings-manager.js).

## Agents and extension configuration locations

- Pi **core** loads user `<agent-dir>/extensions/`, project `.pi/extensions/`, explicitly listed `settings.json` `extensions`, and declared package extensions; project config is trust-gated. Also documented `<agent-dir>/mcp.json` and project `.pi/mcp.json` for MCP; `settings.json` holds Pi's own resource/package configuration. Core's documented agent-dir layout has **no `agents/*.md`** or single generic `extensions/<name>/config.json` specification; third-party extension config is extension-defined. It writes/reads global `<agent-dir>/subagents.json` and project `<cwd>/.pi/subagents.json`: project fields override global fields, missing fields use package defaults; `/agents` UI writes **project** file, not global. ## Package compatibility metadata

- Pi's documented package `package.json` `pi` manifest declares **resource paths** (`extensions`, `skills`, `prompts`, `themes`), plus optional gallery image/video and `pi-package` keyword; the installed core `readPiManifest` parses **only those four resource arrays**, not `pi.version` or a Pi engine requirement. Core `package-manager.js` has no Pi-version compatibility check in its install/update/manifest resolution paths. These are observations about Pi's own 1.4.0 checks, **not** a promise about future versions or external package managers. [packages.md](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#create-a-package), [pi-manifest.js](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/pi-manifest.js), [package-manager.js install/npm args](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L1483-L1547).
- Package authors can use ordinary npm `peerDependencies` to **express** Pi API compatibility: installed `@tintinweb/pi-subagents` declares `@earendil-works/pi-coding-agent: ">=1.1.0"` (and peers for other host packages). Pi 1.4.0 explicitly suppresses peer dependency installation/resolution on its managed npm installs (`--legacy-peer-deps` with npm; analogous settings for pnpm/Bun), so this peer is **not enforced by Pi as a minimum Pi version**. Ordinary npm `engines` constraints, if present, are the invoked package manager's concern and can depend on its configuration; no Pi-specific enforcement was found. [subagents `package.json`](file:///Users/ivanhx/.pi/agent/npm/node_modules/@tintinweb/pi-subagents/package.json), [Pi dependency guidance](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/docs/packages.md#declare-dependencies), [package-manager.js managed install args](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js#L1483-L1525).

## Controlled observations and limits

All `pi` experiments ran from a new `mktemp -d` cwd with a separate `PI_CODING_AGENT_DIR=$(mktemp -d)`, `PI_OFFLINE=1`, `PI_TELEMETRY=0`, `PI_SKIP_VERSION_CHECK=1`; only temporary settings/package files were written. A local dummy package was installed/removed only in these temporary dirs. `pi install --local --no-approve ./pkg` refused writes, while `--approve` succeeded. Source spelling/identity test imported installed Pi's `dist/utils/git.js` `parseGitUrl` read-only; it returned `git:github.com/x/y` as the normalized host/path key for the five URLs above. Source-match/deduplication implications were independently checked against [package-manager.js](file:///Users/ivanhx/.nvm/versions/node/v24.14.1/lib/node_modules/@earendil-works/pi-coding-agent/dist/core/package-manager.js); no public git checkout/update was performed.

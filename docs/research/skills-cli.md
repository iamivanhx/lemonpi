# `skills` CLI install/update/readiness research

## Summary

For v1.7.4, re-running `add <source> -g -a claude-code pi -y` installs/overwrites selected skills, not a no-op and not a source-scoped update: removed upstream skills are not automatically pruned. `update -g` checks every tracked global skill (optionally filtered by **skill name**, not repository); `ls -g --json` is the offline inventory. Pi uses `~/.agents/skills`, Claude Code links there from `CLAUDE_CONFIG_DIR/skills` (or `~/.claude/skills`); global source metadata is in an XDG-overridable v3 lock.

## Version and evidence

`npm view skills` returned 1.7.4, distributed from `https://registry.npmjs.org/skills/-/skills-1.7.4.tgz`; checked the published package and public GitHub tagged source. GitHub annotated tag `v1.7.4` has tag object `31b74517250aec1d2a4be7801fa70b08535ad0e5` and resolves to commit `a80e4c9d12d607631249d4d7d059f835d4b2f13a`; the release was published 2026-10-19. ## Re-running `add` and noninteractive behavior

The documented `-y` skips all confirmation prompts; `--all` installs every skill to every agent without prompts. `-a claude-code pi` selects those two agents; `-g` is global. Without `-y`, when targets differ the CLI prompts for symlink/copy and for confirmation even with explicit scope, agents and skill; interactive prompts need a TTY, so use `-y` for unattended use. In v1.7.4 source the `!options.yes` guards cover those prompts; `--json` explicitly requires `--yes`. [CLI commands](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/commands.md#skills-add), [add source](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L1987-L2025), [confirmation](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L2142-L2152), [JSON guard](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L1507-L1530).

**Isolated public-repo experiment (v1.7.4):** running `add vercel-labs/skills -g -a claude-code pi -s find-skills -y` twice with disposable `HOME`, `XDG_STATE_HOME`, `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, npm cache and gh config exited **0 both times**; the second output said `overwrites: Claude Code, Pi` and replaced the canonical directory, retaining one lock entry and its `installedAt` but changing `updatedAt`. Thus same-name installs overwrite (not strict filesystem idempotence). Without `--skill`, `-y` selects **all discovered skills**, including new ones; removed upstream skills are **not** explicitly pruned by the add loop (inference from selection/install and lock-write code, not verified by mutating an upstream repo). Implementation removes/recreates installed directories and rewrites lock timestamp. [selection](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L1707-L1744), [installer](https://github.com/vercel-labs/skills/blob/v1.7.4/src/installer.ts#L198-L207), [lock](https://github.com/vercel-labs/skills/blob/v1.7.4/src/skill-lock.ts#L177-L194).

## `update -g` scope

Documentation says `update -g` updates global skills; named arguments filter by **skill name**, not source repository. Source loops iterate every matching tracked global skill, grouped by source/ref; changes are reinstalled, unchanged skills are checked but not rewritten. If no scope flag, `update -y` or non-TTY chooses project when project skills are detected, otherwise global; named skills without scope search both scopes. Deleted upstream skills prompt for removal, but `-y`/non-TTY **skips deletion**. `update -g` cannot constrain by source directly (workaround: enumerate names from the lock then pass names, subject to name collisions). [CLI commands](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/commands.md#skills-update), [scope](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L121-L155), [global filter/group/check](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L496-L701), [deletion](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L260-L299).

## Global installation paths, links, and metadata

Docs list Claude Code global `~/.claude/skills/` and Pi global `~/.agents/skills/`. Source sets `claudeHome = CLAUDE_CONFIG_DIR || ~/.claude`, and Pi is a universal agent, so `getAgentBaseDir` returns the canonical `~/.agents/skills/` for Pi regardless of `PI_CODING_AGENT_DIR` (no reference to that variable in CLI source). With both agents and default `-y` method, one actual copy at `~/.agents/skills/<name>` and a symlink at `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/<name>`; `--copy` requests copies. Observed this layout in isolated public test; an isolated `PI_CODING_AGENT_DIR` remained empty. [agents](https://github.com/vercel-labs/skills/blob/v1.7.4/src/agents.ts), [installer](https://github.com/vercel-labs/skills/blob/v1.7.4/src/installer.ts#L129-L186), [docs](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/agents.md#supported-agents).

Global manifest is `${XDG_STATE_HOME}/skills/.skill-lock.json` when set, otherwise `~/.agents/.skill-lock.json`, **not** in the canonical skills directory. v3 JSON has `version`, `skills` keyed by skill name, optional `dismissed` and `lastSelectedAgents`; each skill records `source`, `sourceType`, `sourceUrl`, optional `ref`/`skillPath`, `skillFolderHash`, `installedAt`, `updatedAt` (and optional plugin fields). Older (<v3), missing, or unreadable lock reads as empty; global installation can succeed despite lock-write failure, so lock alone is insufficient readiness proof. For project install, separate `skills-lock.json` in project root. [global lock implementation](https://github.com/vercel-labs/skills/blob/v1.7.4/src/skill-lock.ts#L1-L118), [add lock failure handling](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L2224-L2277), [project lock](https://github.com/vercel-labs/skills/blob/v1.7.4/src/local-lock.ts).

## Fetch/auth/failure behavior

For **non-allowlisted GitHub owners** (including arbitrary private repos), `add` tries shallow `git clone` over HTTPS for shorthand URLs; for selected owners (`vercel`, `vercel-labs`, `heygen-com`, `remotion-dev`) it first tries blob/snapshot downloads and falls back to clone. GitHub tree/API calls used for hash/update first try anonymously and on auth-retryable 401/404 or rate-limit 403 try explicitly provided `GITHUB_TOKEN`/`GH_TOKEN`, then `gh api`; if update tree fails it falls back to authenticated Git clone. For failed GitHub HTTPS clone classified as an auth failure, CLI checks `gh auth status -h`, tries `gh repo clone`, then SSH with batch mode; direct SSH Git URLs also work. `gh auth token` is **not** executed (earlier issue #523 concerned v1.4.4; current source differs). [add resolver](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L1134-L1216), [tree lookup](https://github.com/vercel-labs/skills/blob/v1.7.4/src/blob.ts#L225-L278), [clone fallback](https://github.com/vercel-labs/skills/blob/v1.7.4/src/git.ts#L295-L382), [docs](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/commands.md#private-repositories), [older bug](https://github.com/vercel-labs/skills/issues/523). Private update 404 failure was reported in v1.5.9 (#1318); the v1.7.4 code explicitly handles private 404 and clone fallback, **but was not tested against any private repository here**. [issue #1318](https://github.com/vercel-labs/skills/issues/1318), [update check](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L555-L666).

Git clone is noninteractive at Git level (`GIT_TERMINAL_PROMPT=0`; SSH fallback defaults to `ssh -o BatchMode=yes`, unless `GIT_SSH_COMMAND` supplied); clone timeout defaults to **300,000 ms** (override `SKILLS_CLONE_TIMEOUT_MS`). The GitHub API/RAW fetch timeout is **10,000 ms** per request; gh auth status has 5-second timeout. A timeout is identified separately as `GitCloneError.isTimeout`, auth failures as `isAuthError`, and other clone errors have neither. **All thrown `add` clone errors exit code 1**, not distinct exit codes for auth vs network; `--json -y` outputs a failed JSON result with an error string (and stderr diagnostics). An isolated request to `https://127.0.0.1:1/nonexistent/repo.git` exited **1**, emitted `status: failed` JSON. No private auth attempt was made; exact auth diagnostics/exit behavior is source-derived, not experimentally verified. [git client/timeouts](https://github.com/vercel-labs/skills/blob/v1.7.4/src/git.ts#L9-L17), [GitCloneError/clone](https://github.com/vercel-labs/skills/blob/v1.7.4/src/git.ts#L92-L113), [add catch](https://github.com/vercel-labs/skills/blob/v1.7.4/src/add.ts#L2459-L2484), [blob timeout](https://github.com/vercel-labs/skills/blob/v1.7.4/src/blob.ts#L59-L60).

## Local readiness commands

`skills ls -g --json` (alias `list`) scans local valid `SKILL.md` directories and joins by skill name against global lock for `source`, `sourceUrl`, `sourceType`; no remote request by this command. In the isolated two-agent install, JSON showed one `find-skills` with `agents: ["Claude Code"]` **without Pi**, despite Pi using the canonical directory: agent attribution depends on detected agents, and the output is not a reliable proof that Pi is selected/installed. Check the actual canonical path plus Claude symlink/target and lock source if readiness must assert both. Empty list prints `[]` and exits **0** (observed after removal), so its exit code alone is not readiness. [list](https://github.com/vercel-labs/skills/blob/v1.7.4/src/list.ts#L79-L139), [scanner](https://github.com/vercel-labs/skills/blob/v1.7.4/src/installer.ts#L1140-L1330).

`skills check` is actually **an alias for `update`** in v1.7.4, not a separate guaranteed read-only offline status command; it calls the remote update flow and may reinstall changed skills. Docs describe it as checking without reinstall, **contradicting current dispatch**: do not rely on it for local readiness or read-only checks. `update -g` may print `All global skills are up to date` even after a source-check exception (caught without incrementing `failCount`), so that line alone is not proof of successful private-repo freshness. No `status` subcommand in CLI dispatch. [CLI dispatch](https://github.com/vercel-labs/skills/blob/v1.7.4/src/cli.ts#L412-L427), [docs check](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/commands.md#skills-check), [update catch/report](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L636-L699).

`skills remove owner/repo -g -y` matches **exact lock `source`** and deletes matching skills locally, no fetch; confirmed with public source in isolation (exit **0**, list `[]`, lock `skills: {}`). `remove -g -a ... -y` can target agents but beware partial removal vs canonical Pi store. [remove matcher](https://github.com/vercel-labs/skills/blob/v1.7.4/src/remove.ts#L40-L71), [remove](https://github.com/vercel-labs/skills/blob/v1.7.4/docs/commands.md#skills-remove).

## Unconfirmed questions

- Private-repo authentication and private update were deliberately **not** exercised; actual credentials/SSO policies, SSH host behavior, API availability, and per-environment network timing must be validated by an authorized user without exposing secrets. Code-supported fallbacks do not prove this particular private repo works.
- Whether another program (Pi itself) uses `PI_CODING_AGENT_DIR` to discover `~/.agents/skills` from a nonstandard agent home is outside the scope of this CLI investigation. `skills` v1.7.4 itself ignores that override.
- No repository-wide automatic upstream deletion sync by re-adding was found; `update -g -y` explicitly skips upstream deletions. The interaction of same-named skills from different sources is constrained by the name-keyed lock and warrants independent review if collisions occur. [global lock](https://github.com/vercel-labs/skills/blob/v1.7.4/src/skill-lock.ts#L52-L62), [deletion](https://github.com/vercel-labs/skills/blob/v1.7.4/src/update.ts#L260-L299).
